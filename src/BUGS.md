# Known problems in the code

Found on 2026-10-18 while writing the XML comments for every public member. A comment has to say what
the code does, so each place where the code does not match its interface (or its own name) was
written down. **None of these has been reproduced by running it unless the entry says so.** Each
one is a reading of the code by the person who wrote its comment.

How an entry is closed: a test that fails first, then the fix, then the entry moves to the
"Fixed" section with the commit. A problem is never closed by editing the interface comment to match
the code, unless the interface comment was the part that was wrong, and the entry says that.

Group letters: **R** real bug, **S** stub that reports success while doing nothing, **Q** needs the
real specification before anyone touches it, **I** the interface comment is probably the wrong part.

### S - stubs that report success while doing nothing

| Where | What |
|---|---|
| `RetroIO.Protocols.X25.Runtime` `SerialTransport.IncomingCall` | The event is still never raised, on purpose like `XotClientTransport.IncomingCall`: a serial Call Request is now taken apart by `SerialLapbLink` and raised and answered once through the line's own X.25 engine (`ProtocolRuntime.OnEndpointIncomingCall`), so raising the transport event too would route it twice |
| `RetroIO.Protocols.X25.Runtime` serial port opening | `PhysicalLayer.InitializeSerialPorts` and `PhysicalLayer.Start` are called by nothing in production, and the runtime constructor starts its transports first, so a serial transport configured through `RuntimeConfig` ends in Error ("interface not active"). It needs a decision on who owns the port |
| `RetroIO.Protocols.X25.Runtime` `SerialTransport.PlaceCall`, `AcceptCall`, `RejectCall` | Still throw; outgoing serial calls are not built (incoming calls are answered by the line's X.25 engine) |
| `RetroIO.Protocols.X25.Runtime` serial role and set-up | X.25 does not say which end of a serial cable is the DCE or who sends the first SABM, so `SerialX25LinkOptions` has no default and the engine does not start until both are set. LAPB values (T1, T3, N2, k, 622 byte limit) are the library's, not from X.25; `LapbLayer` sends an RR after a UA, which comes from the ND bring-up and is not in the X.25 text |
| `RetroIO.Link` `SerialLink` and `SerialLapbLink` | Two serial paths now exist that each run LAPB and an X.25 engine for a serial interface; the config skips an interface that has `X25Link` set so they do not open the same port. Whether to keep both is undecided |
| `RetroIO.Protocols.Xmsg.Api` RR wire framing | `RequestConnection` now returns a client-made nonzero reference and each message carries both sides' references (deduced from the call order in the COSMOS guide, section 4.3), but no RR-LIB capture was found, so the bytes on the wire are still our own framing (see `RrMessageKind`) |
| `RetroIO.Protocols.Econet` `FileServerConfiguration` flag bits | ManyHandle, MdfsFunctions (owner bytes included), AcornDir (text catalogue), AcornHome and MdfsInfo (`*CAT` text) follow PiFS `fs.c`; each object now has an owner and home owner in the shared property bag. | `RetroIO.Protocols.Econet` attribute store | Open choices the sources do not settle: (1) no backend uses native host extended attributes (.NET has no portable call), all six store the `.xat` file, whereas fs.c tries xattr first; Azure blob metadata was not checked as a native option; (2) the bag of a disc root on `CompositeVfs` cannot be written; (3) a `.xat` file holding the JSON text `null` throws `InvalidOperationException` instead of reading as damaged; (4) `SetObjectInfoOperation` still writes load, exec and access for commands 2, 5 and the canonical form, whereas fs.c `fs_set_object_info` (line 5372) sets only the load address for 2, only the exec address for 3 and nothing for 5 |
