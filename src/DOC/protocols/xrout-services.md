How a name becomes an address, how a letter is forwarded, and the SEAT accounting that goes with it. The seat rule is here because getting it wrong costs nothing visible at the time and closes a service hours later.

**Where it sits:** XROUT requests ride as ordinary XMSG messages with the Route option set. See sintran-wire.json for the header.

## The seat law

**XROUT holds a FREE-CONNECTION count for a registered connection port, forwards a letter only while it is above zero, and DECREMENTS IT ON FORWARD - before the receiver has seen a byte of the body.**

**MEASURED** - the real file access server builds its 30 seats this way, captured; and ChatSeatAccountingTests reproduces the whole rule

- **The seat belongs to the ARRIVAL, never to a kind of message.** A letter carrying something other than the expected request, or a body too damaged to decode, never reaches a handler - so no handler can give the seat back. Settling seats per message kind leaks one every time.
- **Keep the seat only if the arrival put somebody NEW in the room.** 'Became a member', not 'was accepted': a member sending a second letter spends a second seat and only one of them is theirs.
- **A leaked seat is invisible when it happens.** No error, no log line, nobody refused. The service is simply one seat smaller for ever, and it surfaces much later as XROUT turning requests away from a service that visibly has room.

> **The only marker:** message type XMROU - the ONLY thing telling a receiver that a seat was spent on this arrival
>
> both sample servers in the COSMOS Programmer Guide (ND-60.164.3) refuse anything that is not XMROU - 'IF MSGTYPE >< XMROU THEN' in PLANC and the same test in FORTRAN - and each then reads the CLIENT's magic from the arrived message to reply directly

## Flows

Generated from the registry, so a ladder cannot name an operation that does not exist.

### Reaching a service you only know by name

The one thing XROUT is for, and where the seat is spent.

> **Proved:** every chat join and every FA connect in this repository

```mermaid
sequenceDiagram
    autonumber
    participant client
    participant XROUT
    participant server
    server->>XROUT: XSNAM
    Note over server,XROUT: at start-up: claim the name, and say how many callers can be held at once
    client->>XROUT: XSLET
    Note over client,XROUT: deliver this to that name
    alt the name is registered and has a free slot
        XROUT->>server: XSLET
        Note over XROUT,server: the free count DROPS HERE, before the server has seen the body
        server-->>client: XRSOK
        Note over server,client: the server answers the client DIRECTLY - it learned the address from the arrival
    else no such name, or it is full
        XROUT-->>client: XRUNN
        Note over XROUT,client: or XRNSP when the slots are all taken
    end
    loop from here on
        client->>server: XRSOK
        Note over client,server: port to port; XROUT is not involved again
    end
    server->>XROUT: XSCNM
    Note over server,XROUT: at shutdown: give the name back
```

> **The slot is spent on FORWARD.** Not on acceptance. If the server does not seat the caller, IT must give the slot back - nobody else will.

> **A leaked slot is silent.** The service just becomes one caller smaller, for ever, and refuses people hours later for no visible reason.
